## 1. 退出登录加确认框 + 移除登录页死链

用户：「退出登录的话应该会有一个提示框 问你是否退出 然后把首页的先逛逛首页给去掉」
（两件事都属于**退出登录流程**：退出该有确认 → 退到登录页后，那一页的「先逛逛首页」该去掉）

### 1.1 排查结果
- **退出确认**：`ZF.logout(confirmText)` **本来就支持**二次确认（传文案才弹）。
  **管理端一直传了**（`admin-common.js` 的「换账号登录」），**用户端没传** → 点一下直接退，没有挽回余地。
- **「先逛逛首页」是死链**：它在 `login.html`，指向 `pages/home.html`；
  而 `home.html` 走 `ZF.initPage → ZF.requireLogin`，未登录会 `setRedirect()` 后立刻跳到 `login.html`。
  ⇒ 用户点了等于什么都没发生，还多一次跳转。`index.html` 里还有个同款「先逛逛」（默认隐藏的降级入口）。

### 1.2 ★做法：升级组件，而不是打补丁
`ZF.confirm` 原本是 `window.confirm(message)` —— 浏览器原生弹窗（样式改不动、阻塞、无法标危险）。
全站有 **22 个调用点**。所以**把它整体换成站内弹窗**：
- **API 完全不变**（仍返回 `Promise<boolean>`）⇒ **22 个调用点一行未改**，全站二次确认一起升级。
- 用项目已有的 Bootstrap 5 Modal 构建（19 页全都加载了 bootstrap.bundle）。
- **渐进降级**：`window.bootstrap` 不可用时退回原生 `window.confirm`，保证「能确认」这件事不丢。
- 细节：`
` → `<br>`（`laws.html` 的同步提示是多行的）；ESC/点遮罩/任何关闭 = 取消（对删除类 fail-safe）；
  焦点落在「确定」上（**与原生行为一致**，避免老用户按回车时预期落空）；
  新增 `opts.danger` → 确定按钮走朱色（主题里朱只用于风险/警示/删除）。
- 文案**允许含 HTML**（调用方约定自行 `ZF.escape` 用户数据，与 `ZF.toast` 一致）。

### 1.5 ★本轮踩的坑（全部已入 MEMORY.md）
1. **★"会真退出登录"的验证套件会污染后续套件**。`verify-confirm.js` 的 A3 会真调 `/auth/logout`
   销毁服务端会话 → 后面共用同一 cookie 的套件**全部被弹到登录页**（`verify-userpages`
   从 17/17 掉到 10/17，看着像代码坏了）。⇒ **每个套件跑之前都重新登录取全新会话**。
2. **★不同套件需要不同的 cookie 占位符映射**。`verify-login.js` 同时要**用户与管理员两份**会话；
   把同一个 cookie 塞进 `__CK__`/`__CKA__` 会让它的角色分流断言假失败。
3. **★不要在被测页面上硬编码"与当天绑定"的断言**。`verify-trend.js` 原来断言
   「并集首尾是 09-08 / 09-22」—— 日期一过 09-23，窗口前移、09-08 落到窗外，断言无辜失败。
   ⇒ 改成校验**结构性事实**（升序、无重复、末位与今天相差 ≤ 1 天）。
4. **CRLF 文件用 LF 锚点会静默匹配失败**（`common.js` 又踩一次，锚点 0 命中）。
5. **探针不能把 pending promise 交给 `awaitPromise: true`**：本想测 `ZF.confirm('a\nb')` 的换行，
   写成 IIFE 返回那个 promise → 脚本会一直等用户点按钮（或等到超时）。要 `return 1` 让 promise 悬空。

## 2. 接入大模型 API（商汤 SenseNova）—— 让问答/小法庭/文书真正「会解决问题」

用户：「我想在系统中接入我的模型api，使其真正拥有解决问题的能力」。

### 2.1 摸清现状（这一步决定了做法）
- **问答原本是「检索 + 模板拼装」**：关键词 ngram → 在 `law_article` 里召回法条 →
  `composeAnswer()` 按模板拼装（结论/依据/建议/免责）。全项目 **0 处**大模型接入痕迹。
- **★关键发现：检索（RAG 的 R）已经现成**，缺的只是**生成**那一步。
  而 `composeAnswer()` 里那段「初步结论」是**写死的固定句子、跟问题完全无关** ——
  这就是「只能给出法条、不能解答问题」的根源。
- 另外两处生成点：小法庭 `buildSummary`（结论模板）、文书 `render`（占位符替换）。
- 连通性实测：**国内模型 API 全部可连**（DeepSeek 探针返回 401 = 请求真到达了，只差 key）；
  `api.openai.com` 超时；本机无 Ollama。最终用户选 **SenseNova**。

### 2.2 三条硬约束（先摸清才动手）
1. **前端会解析回答格式**：`qa.html` 的 `answerHtml()` 把 `【小节名】` 渲染成小节标题、
   末尾 `提示：` 渲染成脚注。
   ⇒ **提示词必须锁死三段式，否则 UI 会退化成一大段没有层次的纯文本**。
2. **小法庭的胜诉概率是算出来的**（base+delta 钳在 35~97）。
   ⇒ **数值必须归算法，只有文字表述交给模型**。
3. **文书起草是占位符替换**（`（此处待补充：X）`），不是生成。
   ⇒ 模型**只该补空字段，绝不动模板的固定条款与格式**。

## 3. 合同审查接入模型 + 管理端「AI 设置」页

### 3.1 合同审查：判定归规则，表述归模型
- 现状：`ContractServiceImpl` 用 `RULES`（12 条关键词规则）逐条扫正文，命中就套**通用话术** ——
  每份合同看到的 `riskDesc`/`suggestion` 一模一样，压根没看用户合同怎么写的。
- **关键发现**：`scan()` 其实已经把命中的**条款原文**抓出来了（`extractClause` → `clauseContent`）。
  把这段原文喂给模型，它就能指出「你这份合同第 15 条具体怎么写的、问题在哪」。
- 做法：`review()` 里 `scan(content)` **保持纯粹**（单测直接依赖它的规则文本）→ 外面包一层
  `enrichByAi(risks)`。新增 `CONTRACT_SYSTEM_PROMPT` / `buildContractUserMessage` / `applyAiText`。
  - 模型返回 **JSON 数组** `[{i, desc, suggestion}]`，按 **`i`（1 起序号）** 回填 ——
    **不用条款号**：同一份合同里「第 6 条」可能被判出两处风险（加班费包干 + 加班审批），用条款号会串。
  - 提示词明令：已给出的法定标准（30%、200%/300%、不超过 2 年）与法条条号必须原样保留。
  - 失败 → 保留规则话术（只 warn）。
- 验证要点：同一份合同跑两条路径，**（等级|条款号|法条ID）逐条完全一致** ⇒ 模型确实没碰判定；
  且 mock 收到的 user 消息里**含合同原文片段** ⇒ 模型确实看到了用户的合同。

   本项目是纯文本渲染，会原样显示出 `**`。**给模型加 `stripMarkdown` 的同时，自己写文案也要守这条。**
6. 拆分敏感：**新增页面前先 grep 验证脚本里的页面清单**（`verify-admin-ui.js` / `verify-admin-real.js`
   各有一份），漏登记就会出现「新页从未被验证过」的盲区。
7. `enhanceSelect` 的 `.val()` 同步靠**常驻 400ms 轮询**（`setInterval` 遍历已注册下拉），
   所以异步渲染后用 `.val()` 赋值也会同步 —— `<select>` 可以放心用于异步填充的表单。

## 4. 管理端「退出」没有确认框 —— 修的是我上一轮的误判

用户：「为什么管理端的退出登录的提示框又不见了」。

### 4.1 真相：**它从来没有过**（不是"又不见"）
`admin-common.js` 里有两个都调 `ZF.logout` 的按钮：
| 位置 | 调用 | 有没有确认 |
|---|---|---|
| **顶栏「退出」**（`renderAdminTopbar`，`#zf-admin-logout`） | `ZF.logout();` | **没有** → 点一下立刻退出 |
| 「换账号登录」（`renderAdminDenied`，非管理员才看到） | `ZF.logout('确定要退出当前账号，换一个账号登录吗？')` | 有 |

**我上一轮就是这么误判的**：只看到 `admin-common.js` 里那一句带文案的 `ZF.logout('…')`，
就下结论「管理端一直是有确认的，用户端漏了」，于是只修了用户端。
`git log -p -S 'zf-admin-logout'` 证实：顶栏那句从**初始提交**起就是裸调用。

**★教训：判断某个行为「有没有」时，必须 grep 出该函数的所有调用点并逐一看参数** ——
同一文件里另一处传了参数，极容易让人以为这个功能一直存在。

### 4.2 修法：不只是补文案，而是把「确认」变成默认（安全默认）
```js
ZF.logout = function (confirmText) {
  var ask = (confirmText === '' || confirmText === false) ? null   // 显式豁免（程序化登出）
          : (typeof confirmText === 'string' ? confirmText        // 自定义文案
          : '确定要退出登录吗？');                                  // ★ 缺省 = 默认文案
  ...
};
```
- 旧写法是「**传了文案才确认**」→ **调用点漏传就等于直接退出**。这类
  「默认不安全、要靠每个调用点自觉」的 API 一定会再漏，所以改成默认安全。
- 同时在 `admin-common.js` 的顶栏也**显式写出文案**，让「退出必须确认」在调用点一眼可见。
- 用户端 `common.js` 那处不变（本来就传了文案）。

### 4.3 验证：`verify-confirm.js` 22 → **33**（新增 G 段「管理端退出」11 项）
```
G1 顶栏「退出」弹出站内弹窗 + 正文含「确定要退出登录吗」+ 未调用原生 confirm
G2 取消后弹窗移除、仍在管理端、仍是 ADMIN 登录态
G3 ★不传文案调用 ZF.logout() 也会确认（安全默认的回归护栏 —— 防的正是这次的 bug）
G4 确定后跳到 login.html；全程无 JS 报错
```

## 5. 工作台「点开记录后回不去」—— 单列布局的返回路径缺失

用户：「我在点推演记录或者合同档案时，我无法通过任何方式返回填写案情或者上传审查界面」。

### 5.1 先看现场（诊断脚本 `workspace/diag-desk-return.js`，双视口 × 双页面）
`court.html` / `contract-review.html` 是同一个「A 工作台」范式：`.zf-desk` 左栏（页签：填写/记录）
+ 右栏（结果，双列时 sticky）。**桌面双列一切正常**，问题只在**单列布局（≤1100px）**：

| 视口 | 点开记录后 scrollY | 左栏 panelTop | 底部「再推演一次」 |
|---|---|---|---|
| 1440×900（双列） | 0（整页不滚动） | 90 → 常驻可见 | 视口内 ✓ |
| 1024×768（单列） | 809 | **-669（滚出视口上方）** | 还需再滚 **638px**（合同页 246px） |

⇒ 单列下点开记录后：结果卡占满视口，**左栏（含页签栏）被滚到视口上方之外**，
而唯一的返回入口「再推演一次」在长报告的最底部（视口下方 246~638px）；
视口内可见的「收起」只清空报告、不回输入。**所以确实"无路可回"**。

根因是 `showResult()` 里那句 `$('#result-card')[0].scrollIntoView({block:'start'})` ——
在单列布局下它等价于"把用户从输入区整个带到报告区，且不给回程"。

### 5.2 修法：把返回入口放到**结果卡头部**（而不是只放底部）
- 结果卡头加按钮 **`#result-back`**（小法庭「返回填写」/ 合同审查「返回上传」），与「收起」并列。
  卡头在 `scrollIntoView` 后一定位于视口顶部**且不会随报告变长而离开视线**。
- 抽出 `backToInput()`：切回左栏**第一个页签** + 把左栏滚回视口 + 聚焦主输入框；
  底部「再推演一次」改为**共用同一个函数**（避免两处行为漂移）。
- ★**必须连滚动一起做**：只切页签的话，用户还停在下方报告处、**根本看不见变化**，
  仍会认为"点了没反应"。

### 5.3 ★★修的过程中又抓到一个会让修复失效的问题：sticky 顶栏 + `scrollIntoView`
`.zf-topbar` 是 `position:sticky; top:0; z-index:20`（实测高 64~68px）。
`scrollIntoView({block:'start'})` 会把元素顶部对齐到 **y = 0** ⇒ **元素最上面那 ~61px 被顶栏盖住**。
而单列下被盖住的恰恰是「卡片头部 / 页签栏」—— 也就是**唯一能点到的返回入口**。
⇒ 新增 `scrollBelowTopbar(el)`：显式扣掉顶栏高度（再留 12px）后 `window.scrollTo`；
`showResult()` 的滚动也一并换掉（否则我新加的按钮同样在顶栏后面）。
桌面双列时整页不滚动，`window.scrollTo` 自然是空操作，不影响原行为。

### 5.4 验证：**新增 `verify-desk-return.js`，78 项全绿**
- 覆盖 **3 档视口（1440 双列 / 1024 单列 / 560 窄屏）× 2 个页面**，每页 13 项。
- ★**用 `document.elementFromPoint` 做命中测试**，而不是只查「元素存在 / display 不为 none」——
  因为元素完全可能"存在且可见"却正好被 sticky 顶栏盖住，只有命中测试能证明它真的点得到。
  实测：单列下点开记录后 `back={"ok":true,"top":99,"cy":114}` ⇒ 按钮在视口内且未被遮挡。
- 关键断言：点记录后返回按钮**点得到** → 点它 → 左栏切回第一个页签 + 面板可见 +
  **页签栏命中测试通过** + 光标落在输入框；底部「再推演一次」等效；「收起」后返回按钮重新隐藏。
- 回归：`verify-userpages` 17/17。`static-check` 全绿。版本号 `20260923c`。
- 对照图：`shots/390-desk-record-single.png`（点开记录后，返回按钮就在报告卡头部）/
  `shots/391-desk-after-back-single.png`（点返回后，上传表单与页签都回到视口）。

### 5.5 ★本轮的坑
1. **★「元素存在且可见」≠「用户点得到」**。sticky 顶栏遮挡这类问题，只有命中测试/截图能发现。
   （本轮如果只做 `getComputedStyle().display !== 'none'` 的断言，会**通过但功能是坏的**。）
2. **★我的探针漏了 `errs` 字段，导致「全程无 JS 报错」这条断言恒失败**（52→48 的 4 条 FAIL
   全是它）。教训同上：断言失败时**先怀疑断言/探针自己**，别急着改被测代码。
3. **同一范式改一个必须查另一个**：`court.html` 与 `contract-review.html` 是复制关系，
   本轮两边的锚点、id、文案都不同（`court-desc` / `cf-content`；返回填写 / 返回上传），
   用「按文件 + 占位符」的脚本一次改两边，避免只改了一个。

## 6. 「还是不行」—— 上一轮修的只是半个问题，双列下页签栏被历史面板整条盖住

用户拿着窄窗口截图再报：「还是不行啊 没有返回的窗口」。

### 6.1 为什么上一轮没修好
上一轮给单列（≤1100px）加了页签栏 sticky（`top:64px`），验证也过了 —— 但**验证的场景是
「点开一条记录 → 结果卡把视口滚走」**。用户实际卡住的是另一个场景：**停在「档案/记录」页签、
往下翻了列表**。此时页签栏随页面滚出视口（top=-218），没有 sticky 就点不到。
⇒ sticky 本身是对的，但只修了「结果卡滚走」这一条路径。

### 6.2 复查时又抓到一个**更隐蔽的双列 bug**
新加的 2b 断言（停在档案页签 + 滚 300px 后页签必须可点）在双列 1440 下 **FAIL**，
命中到 `zf-card__title`。几何实测：

| 视口 | 页签栏 | 历史面板 | 页签中心命中 |
|---|---|---|---|
| 1440 双列 | 90~130 | **absolute top:0 → 90~878，整条盖住页签** | `zf-card__title` ❌ |
| 1024 单列 | 86~126 | static，140~794（不重叠） | `zf-tabs__tab` ✓ |

根因：`.zf-desk__history { position:absolute; top:0; inset:0 }` 从**面板顶端**铺满 ——
它本该只盖「填写/上传」卡片，却连页签栏一起盖了。**双列下切到档案后页签既看不见也点不到**，
和单列是同一个症状、完全不同的病因。

### 6.3 修法（都是 app.css，两处）
1. **`.zf-desk__history` 的 `top: 0 → 54px`**（页签高 40 + 间距 14；单列 media 里已重置为
   static 不受影响）。历史面板从 144 开始，与输入面板起点**完全对齐**（实测 144 = 144），
   页签中心命中回到 `zf-tabs__tab--active`。
2. **`.zf-desk__panel > .zf-tabs` 加 `position:relative; z-index:2`** 当安全网 —— 万一将来
   页签变高又叠上，保证「页签可点」优先于「卡片标题不被压」。

单列 sticky（上一轮的 `top:64px`）保留：实测 1024/560 下滚 300px 后页签 `top:68`、可点 ✓。
527px 下横向溢出 = 0（用户截图里的横向滚动条是缩放或别的宽度，当前无需处理）。

### 6.4 验证：`verify-desk-return.js` 78 → **90**（90/90 全绿）
- 新增 2b/2c 断言：**停在档案页签 + 滚 300px 后页签栏仍可点（elementFromPoint 命中测试）**、
  且滚着的时候点页签就能切回。3 档视口 × 2 页面全过 —— 双列靠让位、单列靠 sticky，一条断言同时防两种病因。
- 回归：用户端 17/17、交互动效 24/24、管理端 148/148。版本号 `20260923e`（纯 CSS，刷新即生效）。
- 凭证图 `shots/392-合同审查-档案页签-窄屏.png`：窄窗口、档案页签、滚过列表，
  页签栏粘在顶栏正下方 ——「上传审查」随时能点。

### 6.5 ★本轮的坑
1. **★★「修好了一个场景」≠「修好了这个问题」**。上一轮的验证只覆盖「点开记录后回不去」，
   而用户卡住的是「翻列表后回不去」。**用户报 UX 问题时，要枚举能到达同一坏状态的所有路径**
   （本例至少 3 条：点开记录、翻列表、切页签后直接想回去），验证要按路径写，不按修复写。
2. **★布局叠加类 bug 只在特定页签状态下暴露**：页签被盖这个问题，只有在「历史页签激活」时
   才出现（输入页签下 history 是 display:none）。**验证状态切换类界面必须逐个页签测命中**，
   只测默认状态会永远发现不了。
3. **★absolute inset:0 的面板会连带盖住「面板外的东西」**（本例是排在它前面的页签栏）。
   写这种铺满定位时，要问一句：容器里除了目标内容还有什么？谁会被我压住？
