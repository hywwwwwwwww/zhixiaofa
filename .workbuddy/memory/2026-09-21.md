### 五、新踩的坑（重要，已追加到 MEMORY.md）
1. **CSS 级联顺序**：追加到文件末尾的基态规则会盖掉上方的 `@media`（同特异性后者胜）。
   基态必须写在媒体查询**之前**。
2. **`cdp.js` 的 `httpGet` 对 `/json/close` 与 `/json/new` 都会抛异常**：
   前者返回纯文本 `Target is closing`；后者用 GET 会返回
   `Using unsafe HTTP verb GET to invoke /json/new`，且 **`/json/new` 要求 PUT**。
   两者都会让内部无条件 `JSON.parse` 抛 SyntaxError 并**逃出 try/catch**
   （异常发生在 promise 回调里）。必须用原生 `http.request` 手写。
3. **多页签截图必须用「该页签自己的 send」**：`Page.captureScreenshot` /
   `Runtime.evaluate` 都应传新页签的 `send`，否则读到/截到的是最初那个 `about:blank`
   页签（表现：`href=about:blank`，让人误判成「导航没生效」）。
4. **CSS 过渡在同一 JS 回合内不推进**：`m.click()` 之后立刻 `getComputedStyle`，
   读到的必然是起始值（`visibility:hidden` / `transform:translateX(-100%)`）。
   必须 `await` 一帧 + `setTimeout(320)` 之后再读，且 `Runtime.evaluate` 要带
   `awaitPromise:true`。
5. **导航后要轮询等 `document.location.href` 变成目标页**，不能只 `sleep` 一个固定值。
6. **`ZF.initAdminTable` 读的是 `page.list`，不是 `page.rows`**：
   桩给错字段会表现为「`total` 有值但表格显示没有找到匹配的记录」的迷惑现象。
7. **`laws.html` 直接调真实业务接口 `/law-articles/*`**（不是 `/admin/*` 那套）；
   `logs.html` 的图表接口是 `/admin/logs/stats`（`{uri:[],slow:[]}`）——
   写桩前必须逐个 grep 页面实际调的 URL。

## 二、「qa / doc-templates / quiz 三页被踢到用户端首页」——**排查完毕，是巡检桩的假阳性**

用户之后又说「帮我看一下管理端界面」。走 8080 真实服务器巡检 9 页时发现

（侧边栏消失、标题变成「首页 - 职小法」），其余 6 页正常 —— 正是用户说的
「没变成目标样子」的症状。**逐层排查后确认：产品没问题，是我的巡检桩不完整。**

### 被排除的 4 类原因（都是实测排除，不是推断）
1. **文件内容**：9 页与源项目 diff 只差版本号；服务器返回的也是新版。
2. **缺 ZF 成员**：9 页用到的 `ZF.*` 在 `common.js`(45) + `admin-common.js`(26) 中**零缺失**。
3. **`ZF.CTX` 推导**：`/admin/` 分支正常，CTX `/zhixiaofa` 正确。
4. **JS 抛错**：`window.onerror` + `unhandledrejection` 抓到的 `errs` **全为空**。

### 真正的根因：`AuthFilter` 白名单 → 同一语义两种 HTTP 状态
`AuthFilter` 有公开只读白名单：
```java
PUBLIC_GET = /api/law-articles, /api/knowledge, /api/doc-templates, /api/quiz, /api/qa
```
- **白名单内**匿名 GET → 过滤器放行 → **Servlet 自己返回 `HTTP 200` + `code=11301`**
- **白名单外**未登录 → 过滤器 `writeUnauthorized` → **`HTTP 401` + `code=11301`**

实测 9 页所调接口的响应形态：
| 接口 | 状态 | 页 |
|---|---|---|
| `/qa/stats` `/quiz/stats` `/doc-templates/stats` | **200 + 11301** | qa / quiz / doc-templates ← **正是这 3 页** |
| `/auth/profile` `/users` `/admin/logs` `/contracts` `/admin/stats/*` | 401 + message | 其余 6 页 |
| `/law-articles/*` `/knowledge` | 200 + 10000 | laws / knowledge（匿名可读，无影响） |

`js/common.js` 是「HTTP 200 → `success`，HTTP 401 → `error`」：
- `success` 分支见 `code===CODE_UNAUTHORIZED(11301)` → `toast` + `setTimeout(ZF.redirectLogin, 900)`
- `redirectLogin()` 读 `sessionStorage.zf_redirect`（此时为空）→ `location.href = login.html`
- **桩让 login 页以为已登录 → 又跳 `pages/home.html`** ⇒ 被"踢出管理端"

**为什么只影响那 3 页**：恰好只有它们会调 `/…/stats` 这三个白名单路径接口。
精确对应，零例外。（`error` 分支里那个 `xhr.status===401` 因为响应体带 `message`
而被 `if` 抢先命中，是**死代码**，所以 401 的 6 页反而只弹 toast 不跳转。）

### 决定性验证：真实会话 9/9 全绿
`POST /api/auth/login {username:'admin',password:'admin123'}`（凭据见 `docs/部署说明文档.md`）
→ JSESSIONID → CDP `Network.setCookie` → 零桩导航 9 页：

```

 OK  users.html           sidebar=true navN=9 rows=10
 OK  qa.html              sidebar=true navN=9 rows=10      ← 之前"被踢"
 OK  contracts.html       sidebar=true navN=9 rows=10
 OK  laws.html            sidebar=true navN=9 rows=10
 OK  knowledge.html       sidebar=true navN=9 rows=10
 OK  doc-templates.html   sidebar=true navN=9 rows=10      ← 之前"被踢"
 OK  quiz.html            sidebar=true navN=9 rows=10 charts=1   ← 之前"被踢"
 OK  logs.html            sidebar=true navN=9 rows=10 charts=2
通过 9 / 9
```
**结论：管理端替换 100% 正确，9 页全部渲染真实数据，产品无缺陷。**

## 七、执行 `sql/data.sql` 重置数据库 + 一次**备份静默失败**的补救

### 7.1 用户请求与前置核查
用户说「@data.sql 现在数据库已经更新 你直接运行这个就行」。**运行前先看清 data.sql 是什么**：
- 全盘搜 `data.sql`：只有项目 `sql/data.sql`(50876B, 09-15) 与源项目同名文件(50204B)，**两者内容完全一致**（673 行，仅行尾不同）
- 结构：**15 处 `DELETE FROM`**（是"重置脚本"，先清空再插种子），**无 DROP/CREATE TABLE**（所以不影响我加的 `seq/source/source_id`）
- 影响预演：`law_article 484→14`、`operation_log 3911→12`、`contract 20→10`、`qa_record 18→12` 等
- 用 AskUserQuestion 让用户确认 → **「跑，重置回种子数据」**

### 7.2 ★教训：备份循环**静默失败**（必须记住）
我在运行前写了个"全量备份"循环：
```python
tables = q("SELECT TABLE_NAME FROM information_schema.TABLES ...").split('\n')
for t in tables:
    q("CREATE TABLE %s_bak_reset_20260921 AS SELECT * FROM %s;" % (t, t))
```
**两个致命问题**：
1. `mysql -N -B` 输出是 **CRLF**，`.split('\n')` 让每个表名尾部带一个 `\r`；
   MySQL 把 `\r` 当空白 → `CREATE TABLE law_article\r_bak_...` 变成
   `CREATE TABLE law_article _bak_...` → **语法错误**
2. 我的 `q()` 把错误吞了（`return out or err`），而打印语句只是我自己拼的字符串，
   **根本没看 SQL 返回值** → 16 张表备份全部失败，却打印得像是成功了

⇒ **规律：任何"批量备份/批量操作"必须逐条检查返回值 + 事后逐张比对行数。**
   已固化为 `tools/db-backup.py`（`.strip()` 剥换行 + 逐表行数自校验，不一致就整体报错退出）。

### 7.3 ★补救：用 binlog 完整还原（本机 `log_bin=ON` 且 `binlog_format=ROW`）
被 `DELETE` 掉的行的**原始值全部记录在 binlog 里**，因此可完整恢复：
- `mysqlbinlog --read-from-remote-server --host/--user/--password --base64-output=DECODE-ROWS -v --start-datetime --stop-datetime <binlog>`
  （重要：`D:\ProgramData\MySQL\...\Data` 读不到权限，**必须用 `--read-from-remote-server` 从服务器读**）
- 解码后每行一条记录块，形如
  ```
  ### DELETE FROM `db`.`tbl`
  ### WHERE
  ###   @1=15
  ###   @2='张三'
  ```
- 写成 `tools/binlog-undelete.py` → 生成 `sql/restore-prereset-20260921.sql`
- **结果：4613 行全部还原**（operation_log 3911 / law_article 484 / contract_risk 30 / … 与重置前逐表吻合）

**解析器踩的两个坑（都写进工具注释了）**：
1. 遇到下一个 `### DELETE FROM` 必须**先把上一块落盘**，否则只保留最后一行（实测 4613 行只抓到 1 行）
2. `### WHERE` 是**块内正常行**，不能当块结束符（否则 `@n=` 全被跳过，抓到 0 行）

**验证手法（值得复用）**：把恢复脚本包进
`SET FOREIGN_KEY_CHECKS=0; START TRANSACTION; <脚本>; <统计>; ROLLBACK;`
**跑完即回滚** —— 既证明脚本语法/列数正确，又不改变现状。实测事务内恢复到
`484/3911/18/20/13/17`，回滚后仍是 `14/16` ✓
